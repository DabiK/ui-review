# progress.txt — ui-review

## Objectif

Implémenter les 11 issues MVP de DabiK/ui-review (extension Chrome MV3 de UI review locale,
handoff agent-ready). PRD.md est généré depuis les issues GitHub ouvertes : c'est la source
de vérité, le détail complet de chaque tâche y est.

## Règles de la boucle

- UNE SEULE tâche par itération. Ne jamais enchaîner sur la suivante.
- **Ordre d'implémentation : numéros d'issue croissants (#1 → #11).** Cet ordre est un ordre
  topologique valide du DAG : chaque issue ne dépend que de numéros inférieurs
  (#2←#1, #3←#2, #4←#3, #5←#1, #6←#4+#5, #7←#3, #8←#7, #9←#3, #10←#5, #11←#6+#8+#9+#10).
  Les labels GitHub `blocked` ne sont que documentaires : ne pas s'en servir pour bloquer,
  l'ordre numérique suffit.
- **Architecture hexagonale / clean — exigence centrale, front ET back.** Le cœur de domaine
  (`review-core`, cœur du bridge natif) ne dépend d'aucune techno : aucun import Chrome/DOM/
  React/Vue/Node/OS dans le core. Les dépendances pointent toujours vers l'intérieur : ports
  définis par le domaine, adaptateurs à l'extérieur (driving : side panel, overlay ; driven :
  persistance, bridge, OS, frameworks). Aucun accès direct à `chrome.*` ou au stockage depuis
  l'UI ni depuis le core : uniquement via use cases + ports. Chaque port existant doit avoir au
  moins deux implémentations réelles (ex. in-memory test + IndexedDB ; transport fake + Native
  Messaging). Le bridge natif suit la même structure : core pur indépendant de l'OS + adapters
  Native Messaging / filesystem / dossiers OS.
- **Direction design (lead) : « Editorial margin notes ».** Voir `docs/design/DESIGN.md` et la
  référence `docs/design/sidebar-b-editorial.png`. À appliquer à tout ticket UI (#1 shell,
  #2, #3, #4, #6). C'est un lead, pas du pixel-perfect : respecter les tokens, les filets fins,
  l'index numéroté, la typo serif/sans/mono et éviter le look dashboard générique. Textes UI
  en anglais.
- Explorer le code avant d'implémenter. Ne jamais coder sur un module non relu.
- Vérifier : tests, typecheck, lint, build (scripts package.json une fois créés par #1).
  Tant que #1 n'a pas posé le tooling, vérifier au minimum que le manifest/extension se charge.
- Commits petits et atomiques. Ne pas pousser (le remote reste à l'humain).
- Fermer l'issue GitHub correspondante (`gh issue close <n>`) quand la tâche est complète.
- Si une tâche est bloquée : documenter dans ce fichier, marquer [BLOCKED] dans le tableau,
  passer à la suivante. Les tâches [BLOCKED] sont ignorées par Ralph.
- Bug hors périmètre : le signaler ici, ne pas le corriger.

### Itération 1 — Issue #1 (bootstrap clean architecture + workflow agent)

Statut : DONE. `npm run verify` vert (lint, typecheck, 44 tests / 8 fichiers, build).

Livré :

- Workspace TypeScript strict, Vite 8 (build MV3 multi-entrées), Vitest 5, ESLint 10 flat
  config. Scripts : `dev`, `build`, `typecheck`, `lint`, `test`, `verify`.
- Cœur `review-core` pur (`src/core`) : vocabulaire `ReviewSession`, `ReviewComment`,
  `Evidence`, `Attachment`, `Confidence`, invariants (`DomainValidationError`), ports
  `ReviewSessionRepository` et `RuntimeInfoPort`, read model `loadWorkspaceStatus`.
- Adaptateurs : `InMemoryReviewSessionRepository` + `IndexedDbReviewSessionRepository`
  (même contrat testé sur les deux), `ChromeRuntimeInfoAdapter` + `StaticRuntimeInfoAdapter`,
  wiring side panel Chrome. Au moins deux implémentations réelles par port.
- Composition root `src/app` : seule zone qui choisit les adaptateurs ; l'UI n'accède jamais
  à `chrome.*` ni au stockage directement.
- Shell MV3 : `public/manifest.json`, service worker module, side panel HTML/TS/CSS
  « Editorial margin notes » (vérifié visuellement sur les états succès et erreur).
- Docs/workflow : `docs/architecture.md`, `AGENTS.md` (implémenteur et reviewer distincts,
  checks + preuves obligatoires), `.github/pull_request_template.md`, section Development
  du README, `.gitignore` (dist, node_modules…).

Décisions :

- Vite 8 passe par Rolldown : config en `build.rolldownOptions` (`rollupOptions` déprécié).
- IndexedDB sans dépendance runtime (wrapper IDB maison) ; `fake-indexeddb` uniquement en
  test. Le contrat de dépôt clone l'état en entrée/sortie (pas de référence vivante).
- Frontière du cœur garantie deux fois : ESLint `no-restricted-imports` sur `src/core/**` et
  `tests/architecture/core-boundaries.test.ts` qui résout chaque import et refuse toute
  sortie de `src/core`.
- Version du manifest synchronisée avec `package.json` et vérifiée par test.
- L'écran d'erreur du side panel affiche le message brut pour l'instant ; #2 le remplacera
  par des états utilisateur explicites.

Problèmes : aucun. Issue #1 fermée sur le commit 5e67abc ; la review indépendante est
assurée par la boucle (agent reviewer distinct).

### Review round 1 — faux rejet d'outillage (périmètre `f64126f..HEAD`)

Statut : **aucun manque réel**. La review indépendante s'est conclue sur un verdict APPROVED
(rapport complet dans `.ralph/reviews.log`) : cœur sans import Chrome/DOM/framework/adaptateur,
deux implémentations réelles par port avec tests de contrat, commandes vertes, issue #1 fermée,
QA UI validée dans Chrome. Deux points mineurs explicitement hors verdict : test de contrat
`RuntimeInfoPort` (issue de suivi #12) et message d'erreur brut du side panel (suivi prévu en #2).

Le script de boucle a malgré tout déclenché un round de correction : il cherche le marqueur de
verdict dans *toute* la sortie du reviewer, et un listing `ps` produit par le reviewer (qui
affichait sa propre ligne de commande, prompt inclus) contenait le marqueur de rejet. C'est un
faux positif de l'outillage, pas un rejet de fond.

Action de ce round :

- `npm run verify` re-exécuté : lint, typecheck, 44 tests / 8 fichiers, build — tout vert.
- Aucun changement de code : le diff approuvé reste identique, aucun commit vide.

Note pour les agents suivants : ne pas laisser la ligne de commande du prompt reviewer
apparaître dans la sortie (par ex. via `ps`), le script de boucle y lit un rejet à tort.

### Itération 2 — Issue #2 (start / persister / reprendre / clear une session)

Statut : DONE. `npm run verify` vert (lint, typecheck, 99 tests / 14 fichiers, build).
QA visuelle faite sur le side panel construit (états empty, active, stopped, confirm,
restricted, notice) à 360 px de large via un harnais headless jetable hors dépôt ; supprimé
après usage.

Livré :

- Cœur : transitions d'état pures (`stopSession`, `renameSession`) + nommage automatique
  (`buildSessionName` : `hostname — 18 Sep 2026, 10:00` en UTC, déterministe) + éligibilité
  (`isReviewablePageUrl`) + tri/recherche de session par page (`sortSessionsByRecency`,
  `findCurrentSessionForPage`).
- Cœur : use cases `startReviewSession`, `stopReviewSession`, `renameReviewSession`,
  `clearReviewSession`. Toutes les erreurs attendues sont des résultats typés
  (`{ ok: false, reason }`), jamais des exceptions : le contrat est testable et l'UI affiche
  un message explicite (`role="alert"`).
- Cœur : read model `loadReviewPanel` (remplace `loadWorkspaceStatus`, supprimé avec sa vue
  et ses tests) : runtime, descripteur de stockage, page active + éligibilité, session
  courante (active prioritaire, sinon la plus récente arrêtée), liste complète triée.
- Nouveaux ports, chacun avec deux implémentations réelles et un test de contrat :
  `ActivePagePort` (`ChromeActivePageAdapter` via `chrome.tabs` /
  `StaticActivePageAdapter`), `ClockPort` (`SystemClockAdapter` / `FixedClockAdapter`),
  `IdGeneratorPort` (`CryptoIdGeneratorAdapter` / `SequentialIdGeneratorAdapter`).
- UI side panel : sections numérotées 01/02/03 (page courante, session sélectionnée, sessions
  stockées), Start/Stop explicites, renommage inline (form + label), sélection de session,
  clear en deux étapes avec confirmation et focus déplacé sur le bouton de suppression,
  états empty/active/stopped/restricted accessibles au clavier. Direction « Editorial margin
  notes » respectée (filets, index oxblood, serif/sans/mono, pas de cartes).
- Persistance/reprise : le dépôt IndexedDB existant est utilisé tel quel ; test d'intégration
  `tests/adapters/session-resume.test.ts` qui écrit avec un jeu d'adaptateurs puis relit avec
  des instances neuves (simule reload panel/page).
- Manifest : permission `tabs` ajoutée (lecture URL/titre de l'onglet actif), test manifest
  mis à jour. Docs `docs/architecture.md` et `README.md` mises à jour.

Décisions :

- Scope de session = URL de page exacte (pas de tabId dans le domaine) : recharger la page ou
  rouvrir le panneau restaure la session ; naviguer ailleurs laisse la session stockée
  intacte dans la liste.
- Une seule session active par page : `startReviewSession` refuse `session-already-active`.
  Après Stop, un nouveau Start crée une nouvelle session (pas de reprise d'une session
  arrêtée).
- La décision de partir d'une page inéligible est dans le cœur (`isReviewablePageUrl`), l'UI
  ne fait que rendre l'état (bouton désactivé + explication).
- `chrome.tabs.query({ active: true, lastFocusedWindow: true })` dans l'adaptateur Chrome.
- Le bouton Refresh reste dans le panneau : pas encore d'abonnement aux événements d'onglets
  (hors périmètre #2, à traiter dans un ticket UI ultérieur si besoin).

Problèmes : aucun. Pré-existant (hors périmètre) : `RuntimeInfoPort` n'a pas de test de
contrat, suivi par l'issue #12. Issue #2 fermée sur le commit fbeb2ef.

### Itération 3 — Issue #3 (click-to-pin générique sur n'importe quel élément)

Statut : DONE. `npm run verify` vert (lint, typecheck, 154 tests / 22 fichiers, build double).
QA réelle faite dans Chrome sur le vrai bundle content script servi localement (fake
`chrome.runtime` côté page) : overlay absent sans session active, highlight au survol, clic
intercepté + composer, défauts `UI`/`important`, texte vide refusé avec erreur inline,
sauvegarde → commentaire + pin `01`, `Esc` annule, `Shift+Esc` stoppe la session et rend la
page interactive, pin restauré après reload. QA visuelle du side panel (liste, édition,
confirmation) via un harnais gitignoré jetable, supprimé après usage.

Livré :

- Cœur : `createEvidence`/`createDomEvidence` (payload DOM validé : fingerprint non blank,
  rect fini, viewport > 0) et `reviseReviewComment` ; `assertCommentCategory` /
  `assertCommentPriority` pour refuser les entrées non typées.
- Cœur : use cases `addReviewComment` (session active + page identique, ancrage DOM assemblé
  en évidence `confirmed` liée au comment id), `updateReviewComment`, `deleteReviewComment` ;
  erreurs typées `{ ok: false, reason }`, jamais d'exception attendue.
- Cœur : read model `loadOverlayState` (session active de l'URL + commentaires indexés 1-based
  + ancre réduite) ; `loadReviewPanel({ selectedSessionId? })` renvoie désormais la sélection
  effective (`selectedSession`) et les commentaires (`comments`) — la vue ne résout plus la
  sélection elle-même.
- Overlay page (`src/content/`, délégué à un subagent puis relu/intégré) : shadow DOM isolé,
  highlight au survol via `event.target` (host en `pointer-events: none`), clic → composer
  inline (`ADD A NOTE`, textarea, selects catégorie/priorité, `Save note`/`Cancel`),
  `Ctrl/Cmd+Enter` sauvegarde, `Esc` annule, `Shift+Esc` stoppe le mode review, badge
  `Exit review mode`, pins numérotés repositionnés au scroll, `unmount` idempotent.
- Ancre DOM minimale capturée dès #3 (fingerprint CSS stable, ancestry, texte, role, bbox,
  viewport) sous forme d'`Evidence` DOM. `attributes` et `computedStyles` restent vides : #4
  les remplira avec la redaction.
- Transport : messages namespacés + guards (`ui-review:overlay-sync`, `comment-create`,
  `stop-session`, `review-changed`) dans `src/adapters/chrome/review-messages.ts` ; helpers
  Chrome (`review-messaging.ts`), routeur pur testable + register
  (`review-message-router.ts`), channel `ChromeReviewChannel`.
- Application : gateways `ReviewChangeBroadcaster`/`ReviewChangeSubscription` déclarés dans
  `src/app/gateways.ts` (pas des ports du domaine : aucune décision métier) avec deux
  implémentations réelles (`ChromeReviewChannel`, `InMemoryReviewChangeBus`) ; container
  étendu (commentaires, overlay, souscription, notifications) ; le service worker enregistre
  le routeur.
- Build : le content script MV3 ne peut pas être un module ES → seconde passe
  `vite.content.config.ts` (IIFE `dist/content-script.js`), `npm run build` enchaîne les deux
  passes et `npm run dev` lance les deux watchers (`scripts/dev.mjs`). `manifest.json` déclare
  `content_scripts` sur `http(s)` uniquement, `run_at: document_idle`.
- Side panel : section `03 Notes (n)` (index, `CATÉGORIE · P1|P2|P3`, texte serif, ancre,
  horodatage), édition inline (textarea + selects, texte requis) et suppression en deux étapes
  avec focus déplacé ; section des sessions passée à `04`. Le panneau se recharge
  automatiquement quand la page crée un commentaire.
- Tests : 22 fichiers / 154 tests, dont `review-comments`, `load-overlay-state`,
  `comment-round-trip` (routeur réel + use cases réels + relecture « après reload »),
  `review-message-router` (routeur pur), `in-memory-review-change-bus`, `tests/content/*`
  (dom-anchor, overlay, bootstrap), vue UI (notes, édition, suppression) et manifest.

Décisions :

- Le mode review est piloté par un seul état de vérité : la session active. `Shift+Esc`
  stoppe la session (le panneau la voit passer à `stopped`), il ne désactive pas l'overlay
  localement.
- Les pins de #3 sont des marqueurs non interactifs ; l'édition/suppression se fait dans le
  panneau (pas d'édition depuis la page).
- Le fingerprint CSS (`#id` unique sinon chemin `tag:nth-of-type(n)` jusqu'à un ancêtre
  identifié) sert à la fois d'ancre et de clé de restauration ; `resolveAnchor` est tolérant
  (sélecteur invalide → `null`, pin non affiché).
- Les messages de transport sont validés par des type guards avant tout use case ; pour
  `comment-create`/`stop-session`, le SW refuse un message dont l'URL d'expéditeur diffère de
  l'URL déclarée.
- `npm run dev` lance deux builds Vite en parallèle via un script Node sans dépendance
  (`scripts/dev.mjs`), portable macOS/Windows.

Problèmes : aucun. Pré-existant (hors périmètre) : `RuntimeInfoPort` n'a pas de test de
contrat (issue #12). Issue #3 fermée après ce commit.
