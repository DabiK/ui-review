# progress.txt — ui-review

## Objectif

Implémenter les 11 issues MVP de DabiK/ui-review (extension Chrome MV3 de UI review locale,
handoff agent-ready). PRD.md est généré depuis les issues GitHub ouvertes : c'est la source
de vérité, le détail complet de chaque tâche y est.

## Règles de la boucle

- UNE SEULE tâche par itération. Ne jamais enchaîner sur la suivante.
- **Ordre d'implémentation : numéros d'issue croissants (#1 → #11).** Cet ordre est un ordre
  topologique valide du DAG : chaque issue ne dépend que de numéros inférieurs
  (#2←#1, #3←#2, #4←#3, #5←#1, #6←#4+#5, #7←#3, #8←#7, #9←#3, #10←#5, #11←#6+#8+#9+#10).
  Les labels GitHub `blocked` ne sont que documentaires : ne pas s'en servir pour bloquer,
  l'ordre numérique suffit.
- **Architecture hexagonale / clean — exigence centrale, front ET back.** Le cœur de domaine
  (`review-core`, cœur du bridge natif) ne dépend d'aucune techno : aucun import Chrome/DOM/
  React/Vue/Node/OS dans le core. Les dépendances pointent toujours vers l'intérieur : ports
  définis par le domaine, adaptateurs à l'extérieur (driving : side panel, overlay ; driven :
  persistance, bridge, OS, frameworks). Aucun accès direct à `chrome.*` ou au stockage depuis
  l'UI ni depuis le core : uniquement via use cases + ports. Chaque port existant doit avoir au
  moins deux implémentations réelles (ex. in-memory test + IndexedDB ; transport fake + Native
  Messaging). Le bridge natif suit la même structure : core pur indépendant de l'OS + adapters
  Native Messaging / filesystem / dossiers OS.
- **Direction design (lead) : « Editorial margin notes ».** Voir `docs/design/DESIGN.md` et la
  référence `docs/design/sidebar-b-editorial.png`. À appliquer à tout ticket UI (#1 shell,
  #2, #3, #4, #6). C'est un lead, pas du pixel-perfect : respecter les tokens, les filets fins,
  l'index numéroté, la typo serif/sans/mono et éviter le look dashboard générique. Textes UI
  en anglais.
- Explorer le code avant d'implémenter. Ne jamais coder sur un module non relu.
- Vérifier : tests, typecheck, lint, build (scripts package.json une fois créés par #1).
  Tant que #1 n'a pas posé le tooling, vérifier au minimum que le manifest/extension se charge.
- Commits petits et atomiques. Ne pas pousser (le remote reste à l'humain).
- Fermer l'issue GitHub correspondante (`gh issue close <n>`) quand la tâche est complète.
- Si une tâche est bloquée : documenter dans ce fichier, marquer [BLOCKED] dans le tableau,
  passer à la suivante. Les tâches [BLOCKED] sont ignorées par Ralph.
- Bug hors périmètre : le signaler ici, ne pas le corriger.

### Review round 2 — correctifs issue #3 (clear + URL avec fragment)

Statut : DONE. `npm run verify` vert (lint, typecheck, 161 tests / 24 fichiers, build double).

Deux manques bloquants relevés par la review indépendante, corrigés seuls (aucune nouvelle
tâche) :

1. **Clear d'une session active ne synchronisait pas l'overlay page.** `clearSession()`

### Review round 3 — durcissement de la redaction des URLs (issue #4)

Statut : DONE. `npm run verify` vert (lint, typecheck, 221 tests / 27 fichiers, build double).

Manque bloquant relevé par la review indépendante : `redactUrlSecrets` ne traitait que les URLs
absolues http(s). Trois fuites possibles dans l'évidence DOM :
`https://host/path#access_token=…` (paramètre de fragment), `/path?token=…` (relatif) et
`//host/path?token=…` (protocol-relative) restaient verbatim, donc un attribut `href`/`src`
pouvait persister un secret.

Corrigé dans `src/core/model/redaction.ts` :

- URLs absolues http(s) : credentials, query et **fragment** redactés ; un fragment de type
  hash-route (`#/route?access_token=…`) est scindé pour ne réécrire que sa query.
- Références relatives (`/path?token=…`, `path?token=…`, `?token=…`, `#token=…`) : fallback
  textuel sur la query et le fragment (`URLSearchParams`), la forme d'origine est préservée
  quand rien n'est redacté.
- Références protocol-relative (`//host/path?token=…`) : credentials `user:pass@` supprimés
  puis query/fragment redactés textuellement.
- Schémas non http(s) (`mailto:`, `data:`, `javascript:`) et valeurs non URL : inchangés.
- `redactAttributes` applique ce gate à toute valeur d'attribut non sensible : à ce commit,
  `href`/`src` http(s), relatifs et protocol-relative ne peuvent plus laisser passer un secret
  (limite connue à ce stade : les autres schémas — deep links, `wss:`, `ftp:` — restaient
  verbatim, corrigée au round 4) ; `createEvidence()` reste la porte unique.

### Review round 4 — redaction pour tous les schémas URL (issue #4)

Statut : DONE. `npm run verify` vert (lint, typecheck, 229 tests / 27 fichiers, build double).

Manque bloquant relevé par la review indépendante : `redactUrlSecrets` court-circuitait tout
schéma non http(s) via `SCHEME_PREFIX_PATTERN`, donc `myapp://callback?access_token=…`,
`slack://open?token=…`, `wss://host/socket?token=…` ou `ftp://user:pass@host/?token=…`
survivaient verbatim dans l'évidence DOM (attributs `href`/`src`/`action`).

Corrigé dans `src/core/model/redaction.ts` :

- `redactUrlSecrets` parse désormais toute valeur acceptée par `new URL`, quel que soit le
  schéma (`http(s)`, `ftp`, `ws(s)`, deep links `myapp:`/`slack:`/`vscode:`…) : credentials,
  query et fragment sont redactés identiquement (`redactParsedUrl`, ex-`redactAbsoluteUrl`).
- `mailto:`, `data:` et `javascript:` sont parsés aussi. Décision explicite : une valeur sans
  paramètre secret reste strictement identique (retour de l'original si rien n'a changé), une
  valeur porteuse d'un paramètre secret est réécrite — ces URLs ne sont jamais exécutées
  depuis l'évidence, le trade-off (réécriture potentiellement lossy d'un `javascript:` porteur
  de secret) est documenté et assumé pour ne laisser aucune échappatoire par schéma.
- Si le parse échoue mais qu'un préfixe `scheme:` est présent, le fallback textuel
  (`redactRelativeUrl`) s'applique sur la partie après le `:` ; sinon comportement inchangé
  (relatif et protocol-relative).
- Limite documentée : `intent://…#Intent;…;S.token=…;end` sépare ses paramètres par `;`, que
  `URLSearchParams` ne découpe pas — un secret imbriqué dans un intent Android n'est pas
  masqué (README + `docs/architecture.md`).

Tests (`tests/core/redaction.test.ts`, 27 tests) : deep link `myapp://…?access_token=…`,
`slack://open?token=…`, `wss://…?token=…`, `ftp://user:pass@…?token=…` aux trois niveaux

link sans query ; non-fuite sur un `javascript:` porteur de `?token=` ; fallback textuel sur
une URL http malformée qui échoue au parse ; le test « unchanged » n'affirme plus qu'une valeur
porteuse de secret reste intacte (`mailto:`/`data:`/`javascript:` sans paramètre secret
uniquement).

Docs : `README.md` et `docs/architecture.md` décrivent le périmètre réel (tous schémas
